# M10.0 — non-live execution transport foundation

## Safety and architecture

M10 adds **operational mechanics, not broker connectivity or permission to trade**.
There is no MT5 SDK, network client, real credential use, order placement, route,
worker registration, deployment, or schema migration in this milestone.

```text
strategy / server-owned decision
  ↓
risk/safety authorization (unchanged evaluateExecutionGates, including M8.7 controls)
  ↓
execution authorization (separate server-side authority; unknown/error = deny)
  ↓
execution transport interface (request-bound, one-use capability required)
  ↓
MT5 adapter boundary [M10: disabled/unavailable, no network implementation]
  ↓
broker [NOT CONNECTED in M10]
```

The test alternative is `ExecutionTransport → DryRunExecutionTransport → local
simulation`, with `mode: 'dry-run'`, `live: false`, synthetic `sim-…` order IDs,
and an explicitly unauthenticated, simulated account/session. It never calls
MT5, a broker, an external price source, or a terminal process. A simulated
acknowledgement is **not** a fill or evidence of broker connectivity.

### Components and integration boundary

- `packages/contracts/src/execution-transport.ts`: provider-neutral interface,
  strict request schemas, IDs, timestamps, connection/session/order states,
  results, sanitized errors and structured audit events. No credential fields.
- `packages/core/src/execution/transport/authorization.ts`: the server-only
  dispatcher parses/freeze-copies requests, resolves fresh gate inputs, calls
  **all existing gates unchanged**, then calls the separate execution authorizer.
  Both submit and cancel require this boundary, including replays. Cancellation
  while stopped is deliberately denied here; this is not a new emergency-close
  policy and cannot override existing safety services.
- The injected `TransportExecutionAuthority` is a **trusted composition boundary**,
  not an HTTP DTO or a user-supplied approval boolean. A future production resolver
  must read authoritative ownership, automation, kill-switch, risk and execution
  records and verify that the exact requested order matches the approved decision.
  M10 supplies no production resolver. Tests use synthetic server fixtures only;
  production entitlements still keep automation OFF.
- The dispatcher issues an opaque, one-use, process-local capability, bound to
  the complete parsed request, operation and transport instance. Forged objects,
  changed parameters, another adapter, or reused capabilities are refused before
  exchange. The adapters **check** authorization; they never **grant** it.
- `adapters.ts`: shared bounded operational state, deadline/cancellation handling,
  strict response validation, audit events, and two non-live implementations.
  `MT5ExecutionTransport` always remains unavailable. `DryRunExecutionTransport`
  has deterministic acknowledgement/rejection and explicit test fault scenarios.
- `config.ts`: validates mode/deadline and refuses live opt-in. API `loadConfig`
  invokes validation only; it does not create/register/enable an adapter.

The existing M8.4 `MT5Transport`, disabled provider composition, intake, registry,
M8.7 safety/risk/kill-switch logic and automation switches are untouched. M10 is
not registered alongside that provider or substituted into its authorization
path. A future production integration must be separately reviewed; no optional
transport can make an execution eligible.

## States, correlation and failure behavior

Connection: `disconnected → connecting → connected` or `unavailable`; explicit
disconnect aborts pending operations. Concurrent connects share one attempt.
Orders: `submitting → acknowledged | rejected | failed`; an acknowledged simulated
order can become `cancelled`. Cancellation failure is not a cancellation; a
rejected cancellation leaves the acknowledged order intact.

Requests carry UUID `requestId`, `executionId`, `correlationId` and an ISO timestamp.
UUID case is normalized. Responses must match all three IDs, carry a valid
response timestamp and an operation-appropriate state/order ID. Extra fields,
unknown states and mismatched identities fail closed. Result/audit timestamps
are generated by the local clock; status is a **local simulated snapshot**, not
broker reconciliation. Session health cannot imply real authentication.

All exchanges have a bounded timeout. Timeouts abort the local signal, but are
not evidence that a future remote operation did not happen. After an exchange
starts, timeout, transport failure or malformed response produces a sticky
`failed` result with `outcomeUnknown: true`. There are **no automatic retries**.
Late responses cannot overwrite that result. Disconnecting does not clear the
idempotency ledger. Audit sink failure stops the operation; after acknowledgement
it cannot authorize a second exchange, and the local status remains queryable.

## Idempotency scope and future blocker

Within one adapter instance, submit reservations are keyed by execution ID and
canonical order parameters, made **before any await/exchange**. Cancellation has
its own execution-ID/order-ID reservation, created only after local preflight
confirms a connected transport and matching acknowledged order. Concurrent twins
share the same promise, including while awaiting audit. Initially invalid
cancellation preflight consumes no reservation or request-ID capacity: wrong IDs,
missing orders and pre-acknowledgement cancellations can be corrected/retried.
Once reserved, request IDs cannot be reused for another operation/execution/payload;
changed payloads fail with `idempotency_conflict`. Submission results/failures and
all **attempted** cancellation results/failures remain cached. A replay returns the **original** acknowledgement IDs and timestamp;
use `orderStatus` for current simulated state.

M10.1 tracks entry into the exchange independently of audit completion. A reserved
cancellation that fails before exchange (including audit failure or disconnect
while awaiting audit) releases only its execution reservation; existing request-ID
bindings remain. This permits an explicit authorized retry, never an automatic
retry. Once exchange is entered, rejection, timeout, malformed response, failure,
or post-exchange audit failure **never** releases the reservation. Submission
reservations are never released by this logic. Disconnect/reconnect epochs also
prevent a request waiting on audit from executing on a replacement connection.

The ledger is bounded (10,000 executions by default, bounded request aliases).
Capacity exhaustion fails closed rather than evicting old identities. It is
**in-memory, per instance, not cross-process/restart durable**. This is sufficient
only for this non-live foundation. Before any future broker transport, use a
durable atomic reservation/acknowledgement ledger, broker client-order identity,
restart reconciliation and explicit resolution of uncertain outcomes. Existing
M8 database idempotency is unchanged; M10 does not claim to replace it.

## Configuration

| Variable | M10 behavior |
|---|---|
| `EXECUTION_TRANSPORT_MODE` | `disabled` by default; `dry-run` is safe; `mt5-live` always fails startup |
| `EXECUTION_TRANSPORT_TIMEOUT_MS` | integer 1–60000; default 5000 |
| `MT5_SERVER`, `MT5_LOGIN`, `MT5_PASSWORD`, `MT5_GATEWAY_URL` | future live-mode presence checks only; **do not set real values in M10** |

Disabled/dry-run modes neither require nor retain MT5 credentials. Explicit
`mt5-live` reports missing configuration by **field name only**; even complete
configuration is refused in every environment, including production. Unknown
modes/timeouts are rejected without reflecting values. The safe factory also
rejects a runtime-forged live configuration. There is no live implementation to
select and no gateway is contacted. Existing SecretManager behavior is untouched.

## Audit and secret handling

An injected synchronous or asynchronous audit sink (`void | Promise<void>`)
receives immutable, allowlisted events:
request/execution/correlation IDs, operation, from/to state, timestamp, non-live
mode, and a fixed sanitized error code/message/uncertainty flag. No order payload,
raw provider response, arbitrary error text, stack, cause, login, password, broker
credential, MT5/API secret, or authentication token is forwarded. Without an
injected sink there is no durable M10 event storage; future live wiring requires
a durable audit sink. Gate denials happen before transport invocation and return
only a sanitized authorization error; existing production gate auditing remains
with the unchanged intake/safety services.

M10.1 awaits every audit callback inside the sanitizing error boundary. Both
synchronous throws and rejected promises become a fresh fixed-message transport
error, without the original message, stack or cause. No sink promise is abandoned
as an unhandled rejection. Pre-exchange audit failure prevents exchange; after an
exchange attempt, audit failure cannot permit a duplicate exchange. A sink that
never settles leaves the operation pending without advancing past that audit;
exchange deadlines do not impose a separate audit deadline. Connection attempts
are reserved before awaiting audit, and disconnect remains authoritative during
all audit waits.

The legacy M8.4 response normalizers (`normalizeMT5Error`, `normalizeMT5Order`
and the MT5 provider health/account paths) were redacted under M10 Gate 10: they
now emit fixed-message, closed-category errors with no `cause`, stack or provider
properties; structured receipts without broker text; allowlisted health reasons;
and configured account identifiers only (see the Gate 10 record in the
[M10 verification report](./m10-verification.md)). M10 does not call them, and
routing real broker data through any path still requires the broker/demo
integration work that remains out of scope.
